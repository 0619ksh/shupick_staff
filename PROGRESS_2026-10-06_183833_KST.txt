SHOEPICK 직원용 앱 진행사항
기준 시각: 2026-10-06 18:38:33 (한국 표준시, KST / UTC+09:00)
프로젝트: shupick_staff
저장소: https://github.com/0619ksh/shupick_staff.git
업로드 대상: main 브랜치

1. 프로젝트 및 공통 구조
- HTML 직원용 화면을 Flutter 태블릿 앱으로 구현하고 앱 이름을 SHOEPICK으로 통일했습니다.
- 고객용 shupick 프로젝트의 Firebase Authentication, FastAPI, MySQL shupick_v2를 공유합니다.
- 서버에서 허용한 직원 직책과 현재 소속 지점만 앱에 표시합니다.
- 교환 기능은 운영 계획에서 제외하고 관련 화면 분기·문구를 제거했습니다.
- 직원 앱 코드와 별도 고객 앱·백엔드·DB 코드의 저장소 범위는 다릅니다.

2. 직원 인증 및 등록
- Firebase 이메일/비밀번호 로그인과 세션 복원을 연결했습니다.
- MySQL 직원 정보, 직책, 현재 지점 배정을 로그인 후 조회합니다.
- 등록 화면에서 이메일·비밀번호·비밀번호 확인·이름·소속 구분·지점·직책을 입력합니다.
- 대리점 지점은 서울 25개 자치구 중 선택하며 본사 선택 시 지점 입력은 비활성화됩니다.
- 등록 시 Firebase 계정 생성과 MySQL 직원·직책·지점 배정 저장을 연결했습니다.
- 현재 테스트 정책은 이메일 인증과 관리자 승인 없이 즉시 활성화입니다.

3. 직책별 구현 업무
- 대리점 직원: 주문 입고, 픽업 결제 코드 확인·고객 수령 완료, 방문 고객 반품 접수 및 상태 조회, 현재 보관 재고.
- 대리점장: 지점 입고·수령·반품 접수·조회, 날짜별 보관 재고.
- 본사 사원: 주문·발송, 고객 조회·구매 및 반품 내역·문의 답변, 반품 검수·테스트 환불, 본사 재고, 구매 품의 작성·상신.
- 본사 팀장: 구매 품의 1차 승인·반려 및 재고 조회.
- 본사 이사: 구매 품의 최종 승인·반려 및 재고 조회.
- 본사 임원: 판매 분석, 재고 및 결재 현황 조회.
- 고객 상품 수령은 QR 스캔이 아닌 픽업 결제 코드 확인 방식입니다.

4. 대시보드 및 레이아웃
- 직책별 요약 카드와 업무 알림을 서버 조회 결과에 연결했습니다.
- 알림과 빠른 업무 버튼에서 해당 업무 화면으로 이동할 수 있습니다.
- 지점 대시보드는 선택 지점의 주문·반품·보관 수량을 집계합니다.
- 한 API가 실패해도 나머지 집계와 대시보드 구조를 유지합니다.
- 실패한 수치는 0으로 표시하지 않고 '—'와 조회 실패 안내를 표시합니다.
- 태블릿 폭 700~1199px은 상단 업무 메뉴, 1200px 이상은 왼쪽 메뉴, 700px 미만은 서랍 메뉴를 사용합니다.
- 카드의 고정 높이를 제거하고 좁은 메뉴·로그인·날짜 선택 배치를 조정했습니다.
- 판매 그래프는 날짜 칸의 최소 너비와 가로 스크롤로 오버플로우를 수정했습니다.
- 긴 이름·데이터가 채워진 화면·글자 크기 150% 조건의 회귀 테스트를 추가했습니다.
- 주문·반품·문의·품의 요약은 API의 최근 100건 범위이며 전체 기간 총계가 아닙니다.
- 임원 판매 분석 기본 조회 범위는 최근 28일입니다.

5. 고객 관리 최신 변경
- 고객 목록 정렬: 최근 주문순(기본), 이름순(가나다), 누적 결제액 높은순, 주문 횟수 많은순.
- 최근 주문순에서 주문이 없는 고객은 마지막에 표시합니다.
- 정렬과 검색은 API가 조회한 최대 200명 범위에 적용합니다.
- 고객 상세를 이름·연락처·주문 횟수·누적 결제액·적립금·최근 주문 정보로 재구성했습니다.
- 구매·반품 내역은 날짜·금액·상태가 구분되는 카드로 표시하며 각각 최근 최대 50건입니다.
- 고객 선택 시 이전 고객 정보를 지우고 조회 중 표시를 제공합니다.
- 고객 문의 확인·답변은 본사 사원 메뉴에서 수행하며 SUPPORT_MANAGE 권한이 필요합니다.

6. 대리점 방문 반품 접수
- 반품은 고객이 수령한 대리점에 직접 방문하여 직원 또는 점장이 접수합니다.
- 반품 메뉴에서 주문번호(픽업 결제 코드) 조회 → 상품·수량 선택 → 사유·상품 상태 입력 → 반품 접수 순서입니다.
- 단순변심은 수령 후 7일 이내, 미착용·훼손 없음·구성품 및 포장 유지 조건을 확인합니다.
- 상품 하자·오배송 사유도 접수할 수 있습니다.
- 서버에서 현재 지점 배정·대리점 직책·수령 완료·구매확정·중복 접수·상품 수량·반품 조건을 검사합니다.
- GET /staff/returns/order 및 POST /staff/orders/{order_id}/returns를 추가했습니다.
- 고객 앱은 방문 안내와 처리 내역 조회를 제공하며 고객 직접 접수 API는 403으로 차단했습니다.
- 접수 상태는 REQUESTED이며 본사 검수로 이어집니다. 접수만으로 환불·재고 복구는 실행되지 않습니다.

7. 본사 반품 검수와 테스트 환불
- 본사 사원은 실물 상태와 검수 메모를 입력하여 승인(APPROVED) 또는 반려(REJECTED)합니다.
- 검수 승인 시 정상 상품은 판매 가능 재고로, 판매 부적합 상품은 격리 재고로 복구합니다.
- 반품 환불 처리 화면에서 승인 반품의 상품별 현금 환불액과 배분 적립금을 확인합니다.
- GET /staff/returns/{return_id}/refund 및 POST /staff/returns/{return_id}/refund/test를 추가했습니다.
- 환불 금액은 원래 주문의 쿠폰 할인·적립금 배분을 사용하여 서버에서 계산합니다.
- 현재 flutter-payment- 거래 키의 테스트 결제만 처리하며 실제 결제사 호출·송금은 수행하지 않습니다.
- 실제 결제사 거래는 테스트 환불 버튼 및 API에서 차단합니다.
- 직원이 확인한 금액과 서버 계산 금액이 다르면 처리를 중단합니다.
- 동일 반품 재시도는 기존 환불 기록을 사용합니다.
- 환불 성공 시 반품은 COMPLETED가 되고 결제 상태와 적립금 복원을 기존 환불 로직으로 기록합니다.
- 만료된 적립금은 복원되지 않으며 쿠폰 할인 금액은 현금 환불액에 포함되지 않습니다.
- 환불 기능에는 REFUND_MANAGE 권한이 필요합니다.

8. 판매 분석 예외 수정
- SQL 집계 수치가 문자열로 전달되어 그래프와 매출 카드에서 as num 변환 예외가 발생하던 문제를 수정했습니다.
- 백엔드는 매출·주문 수·일자별 및 제품별 수량을 정수로 반환합니다.
- 앱은 숫자 또는 숫자 문자열을 읽어 동일한 정수 형식으로 정리합니다.
- 잘못된 숫자 값은 형식 오류로 안내합니다.
- 임원 요약 카드, 판매 그래프, 상품 필터에 대한 회귀 테스트를 추가했습니다.

9. 본사 재고 보충 품의
- 입력 항목을 제품 선택·수량·제목·사유로 변경하고 대리점 선택을 제거했습니다.
- 대리점 API 조회와 품의 생성 요청의 branchId를 제거했습니다.
- 새 품의는 purchase_requisitions.branch_id=NULL로 저장합니다.
- 지점이 없는 품의도 조회되도록 목록의 branches 연결을 LEFT JOIN으로 변경했습니다.
- 기존 품의와 과거 지점 연결 정보는 유지했습니다.
- DB 변경 파일: shupick/database/migrations/027_hq_procurement_without_branch.sql
- 로컬 DB에 해당 nullable 변경을 적용하고 기존 데이터 유지 여부를 확인했습니다.
- 본사 사원 상신 → 팀장 1차 결재 → 이사 최종 결재 순서를 유지합니다.
- 서버는 결재 순서·직책 권한을 확인하고 작성자의 자기 결재를 차단합니다.
- 최종 승인 상태는 APPROVED이며 제조사에 실제 발주를 보내는 연동은 아직 없습니다.

10. 최종 검증 기록
- 직원 앱: flutter test 34개 모두 통과.
- 백엔드: pytest 331개 모두 통과.
- 직원 앱 코드 분석에서 문제 없음.
- 지점 없는 품의 생성·상신·조회, 반품 접수·권한 차단, 환불 재시도·금액 변경·실제 거래 차단, 문자열 숫자 처리를 검증했습니다.
- 로컬 서버를 재시작해 변경 API를 반영했고 /health에서 MySQL shupick_v2 연결 정상 응답을 확인했습니다.
- 실제 DB 승인 반품 2건의 환불 조회 계산을 읽기 검증했습니다. 검증 과정에서 실제 환불 상태는 변경하지 않았습니다.
- 회귀 테스트는 대부분 가짜 API/DB를 사용하며 모든 실제 직원 계정의 종단 간 검증을 의미하지 않습니다.

11. 팀원 적용 절차
- 직원 앱을 받은 뒤 README.md를 따르고 Flutter SDK·Android SDK를 준비해 flutter pub get을 실행합니다.
- 같은 Firebase 프로젝트에서 직원용 Android/iOS 앱 구성을 각자 준비합니다.
- lib/firebase_options.dart, android/app/google-services.json, ios/Runner/GoogleService-Info.plist는 Git 추적 대상이 아닙니다.
- 서버용 서비스 계정 JSON과 .env는 로컬에 보관합니다.
- 별도 shupick/backend의 직원 등록·업무·방문 반품·테스트 환불·판매 분석·지점 없는 품의 API가 포함된 코드가 필요합니다.
- 기존 DB에는 누락된 마이그레이션만 적용합니다. 새 품의 기능에는 027_hq_procurement_without_branch.sql이 필요합니다.
- 데이터가 있는 DB에 스키마 재생성 파일을 실행하지 않습니다.
- 백엔드를 재시작하고 직원 앱을 Hot Restart합니다.
- Android 에뮬레이터 기본 API 주소는 http://10.0.2.2:8000이며 실제 태블릿은 접근 가능한 서버 주소를 지정합니다.
- Firebase 계정·MySQL 데이터·백엔드 코드는 직원 앱 저장소의 git pull로 동기화되지 않습니다.

12. 남은 작업과 업로드 범위
- 실제 결제사 환불, 제조사 실제 발주·입고 연동은 별도 구현이 필요합니다.
- 직원 간 업무 대화·고객 혜택 승인·직원 계정 삭제·권한 변경·수동 재고 조정 화면은 아직 없습니다.
- 즉시 활성화 직원 등록은 테스트 정책이므로 운영 전 등록·권한 부여 정책을 결정해야 합니다.
- 과거 Git 기록에 노출된 Firebase 키의 제한·교체 상태는 Firebase/Google Cloud에서 별도로 확인해야 합니다.
- 이번 업로드는 shupick_staff 저장소의 직원 앱 변경과 이 TXT 기록입니다.
- 별도 shupick 프로젝트의 고객 앱·백엔드·DB 변경은 이 저장소에 포함되지 않으므로 별도로 팀에 공유해야 합니다.

이 문서는 위 기준 시각까지의 누적 진행사항을 기록한 스냅샷입니다.
